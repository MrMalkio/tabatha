## Environment note: `resize_window` does not resize anything here

`mcp__claude-in-chrome__resize_window` reported success but every subsequent screenshot stayed at 1512x788 regardless of the target size requested (tried 420x900, 390x844). This is Malkio's real physical monitor/window, not an isolated preview viewport — there's no OS-level window to resize the way the tool expects. **Practical consequence:** I could not force a genuine narrow/portrait viewport to see the Sidecar's mobile-layout CSS; I could only observe the wide-landscape (1512x788) rendering, which auto-selects Context View by design (`isLarge = width >= 900 && width > height` in `sidecar/src/app/index.tsx`). I confirmed the underlying app view instead via the in-page "Use controls →" override (sets `override='context' | 'app'` in state), which is a legitimate part of the UI, not a workaround — but true small-viewport/mobile-CSS regression testing of the Sidecar remains untested tonight for this reason.

Also observed several times: stray tabs appeared in the shared tab group that I did not create — a `chrome-extension://…/manifest.json` error page, a `chrome://extensions` tab, several `Tabatha - Home` (`chrome://newtab/` override) tabs, and once a `localhost:5173` tab showing a different in-progress preview harness (`V0.0.0-PREVIEW-HARNESS-A`, with a visible `Clocked In NaN:NaN:NaN` bug) that is almost certainly a sibling agent's local dev session bleeding into the same real, shared Chrome window this whole fleet is driving tonight. ## Defects found (with fixes)

| # | Severity | Surface | Repro | Root cause | Fix | Status |

| 1 | **HIGH** | `/download` invite-key check | Enter any token (valid or garbage) in the "Invite key" field on `/download` and click "Check key" → always "Could not reach the check right now. Please try again shortly.", with **zero** network request to Supabase visible and **zero** console error, on every attempt | `site/_headers` has a global `/*` rule setting `Content-Security-Policy` with `connect-src 'self'`, and a separate `/download`-specific rule that *adds* `https://mtdgoahskcibjbhfvofx.supabase.co` to `connect-src`. Cloudflare Pages does not let a more-specific rule *replace* a header a broader rule already set for the same header name — **both** CSP headers are sent, and browsers enforce the **intersection** of all matching CSP headers, so the narrower global `connect-src 'self'` wins and silently blocks the fetch. Confirmed live: a same-page `fetch(location.href)` read back two full CSP policy strings comma-joined by the Fetch API's `Headers.get()`, proving two separate header instances existed in the real response | Added `! Content-Security-Policy` (Cloudflare Pages' documented header-unset syntax) before each override in the `/download` and `/download.html` blocks of `site/_headers`, so the global header is unset before the path-specific one is set. Committed locally on staging (`b4c7663`). **Not yet deployed/verified against a live redeploy** — this is the single biggest thing to re-check after the next site deploy, since every current tester is unable to redeem an invite key or download the staff build through this form | Fixed locally, **needs redeploy + retest** |
